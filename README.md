# Crucible

A Monte Carlo agent society simulator intended to stress test a trust stack at scale. It is designed for an estimated population of hundreds of simulated agents trading, vouching, and defecting over simulated years, with trust rules, escrow, and detection running inside the simulation. Its purpose is to measure the conditions under which bad actors start winning instead of guessing them. That measurement stands as the product purpose, not a current capability.

Status: build in progress. The system lands here as it is built, one verified piece at a time. Design records live in a separate private repo and are not part of this repo.

## Install procedure

The release form of this product is one versioned release archive. That archive does not stand built yet, and no manifest, version file, or final build document stands in this repo today. The archive will be built by the build team from the recorded head of this repo after Step 17 closes and before the first install act of Step 18. When it stands built, the archive will contain the product source in full, the example inputs that travel with the product as fixtures, the licence file, and the final build document, and one manifest inside the archive will list every file it contains with its hash. No second distribution form will ship, and no dependency beyond the host environment stated here will be required at install time. The host environment stands stated in full, in the LP-1 host table values, so an installer can read them at install time: Ubuntu 24.04.5 LTS (VERSION_ID 24.04, codename noble) on kernel Linux 7.0.0-44-generic, with Python 3.12 in the CPython form at exact version 3.12.3, standard library only. Every step below that rests on the archive stands as the procedure for the archive when it stands, and cannot be performed before it stands.

Install in this order:

1. Obtain the release archive and record its identity before installing: the version in three part numeric form, the source commit of this repo the release was built from, and the tree hash of that commit. The archive is the object of this step, and this step cannot be performed before the archive stands.
2. Unpack the archive into the install location on the target host. The archive is the object of this step, no unpack command or tool stands named in the product for it, and this step cannot be performed before the archive stands.
3. Verify the install file by file: hash every installed file and compare each hash against the archive manifest, then compare the manifest against the recorded head the archive was built from. An install whose files do not match the manifest does not stand as installed.
4. Run the deterministic configuration check on the target: read the settings and environment values that deterministic mode requires, as the final build document that the archive will contain lists them, and record each value read beside the value required. An install with any such setting absent, or with any value different from the required value, stands recorded as failed in the same form as a hash check failure, and no later step may cite that install as a conforming install until a fresh check passes.
5. Initialise the three stores the product keeps apart: the sweep store, the pilot store, and the live store. Perform this step through the product store surface: call crucible.mod10.new_store(store_kind), which returns a crucible.mod10.RecorderStore, once for each kind in crucible.mod10.STORE_KINDS, whose values are sweep, pilot, and live, for example new_store('sweep'), new_store('pilot'), and new_store('live'). Each store is initialised as an empty store of its own kind, with no shared index between them, and pilot artefacts are stored apart from sweep results from the first write.
6. Record the form and the source of the first family record and of the assumption inputs, before any run. The first family record enters as a family record in the form the product states at Form 1 in crucible.mod01, supplied by the operator, and a record in that form stands built by crucible.mod12.make_family_record. Assumption inputs enter as assumption records in the form the product states at Form 3 in crucible.mod01.
7. Run the verification command for this repo from the product directory: `python3 -m unittest discover -s tests`. The install stands verified only where the suite result stands recorded as a result, never as an intention. Expected result, stated in full: the suite stands at 440 tests, with 4 failures. In the build tree form the expected result is 391 passes, 45 skipped, and 4 failures. In the product only form the expected result is 389 passes, 47 skipped, and 4 failures. The difference between the two forms is Guards 4 and 6a, which stand down as skips in a tree with no design sibling. The 4 failures are the guard tests 3a, 3b, 3c, and 6d: guard 3a, no real money stake encoding; guard 3b, anchor material only as D-09 scenarios; guard 3c, DQ-164 dependence mark; and guard 6d, core only qualifier. Each of those four stands answered, as scan artefacts, with zero product findings, in the answering record design/steps/step-14-rf13-guard-answers.md (the RF-13 guard answers), and no guard hit stands counted as a pass. The skips stand in skip form only: each skip is a gated limb standing skipped on its stated ground, never a pass, and the skips stand counted by their grounds in that form beside the figures stated here.

No seed is drawn and no run is started at install time while no adoption record stands.

Where verification fails, the install stands recorded as failed, the proof step does not open on it, and the failure is owned by the installer of the product and escalated as a readiness blocker. The register entry for a failed first install states the target end state in one of two named forms, failed version present and unproven, or target uninstalled, and states beside it the verification result that proves that end state. The register entry for a failed reinstall states the target end state in one of three named forms, prior version restored, failed version present and unproven, or target uninstalled, with the proving verification result beside it. An entry stating neither the end state in one of those forms nor its proving result is incomplete and closes no install act. Every install register entry is recorded in the install register at design/registers/install-register.md, in the design repo, and the entry forms this procedure prescribes are filed there. Each entry also records the environment identity, by reference to the Form 4 environment record group: the environment identity as a container image digest or an environment lockfile hash, or, where no digest and no lockfile hash stands, an explicit none value for that field. An entry with the environment identity absent or empty stands incomplete in the same way and closes no install act.

## Operator runbook

The operator procedure for this product stands as the runbook in this section. It is the same procedure the shell surface carries in its runbook record; the shell owns no rule of its own and no result wording of its own, apart from the outside call check outcome wording, which stands in the shell module as its program check form, and every step below is a carriage or checking act, never a computation a core owns.

The shell surface stands as a library surface. Its commands are start_run, start_sweep, read_store, write_store, run_pilot, assemble_report, outside_call_check, store_kind_check, and weekly_headline_count, with flag_evaluation carried on the surface as the tenth named program check, and each one is invoked in the form run_command(command, payload), for example run_command('start_run', {'run_class': 'screening', 'family_id': 'fam-1'}). Each command entry on the surface states its purpose, its required and optional input fields by name, and one example invocation.

1. Read the family record and the run record before any act. The shell carries records and interprets none of them.
2. Start runs and sweeps through the start commands only. While the DQ7-02 adoption record does not stand, every start returns the gated refusal that names its gate, and no run starts.
3. Keep pilot work inside its confinement: timing, conformance, and procedure rates only. Each pilot output carries its pilot confined label in the same artefact as its figure, and pilot artefacts are stored apart from sweep results.
4. Read stores by kind: sweep, pilot, and live. Never resolve a record across stores in one lookup.
5. Run the program checks by name: the store kind check; the flag evaluation, whose inputs and outcome stand written into the stored summary record itself; the weekly headline count, counted from the stored summary records alone; and the outside call check, computed from the dependency manifest and the process and network call log only, certifying only the absence the check reads.
6. Treat every named failure as the result of its act. Report it with its run identifier and its stage, and never present an empty result in its place, and never let a command exit cleanly over a failed run.
7. Make no edit to a sealed family record, to a closed run record outside the flag rule path, or to a checkpoint set outside the deletion rule. Validation reads checkpoint manifests beside the run record to compare seeds, settings, and rule versions.
